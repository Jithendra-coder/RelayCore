# Current limitations

RelayCore is an actively developed prototype. It is not a production workflow product yet.

- OIDC and workspace code is locally tested, but no live identity-provider flow was verified. Email invitations, MFA, recovery, and user account administration are missing.
- GitHub App workspace linking and signed pull-request webhooks, plus Slack OAuth, signed `app_mention` events, and a bounded message action, are implemented and locally tested with mocked provider responses; no live provider credentials are configured. Only GitHub `opened`, `reopened`, `synchronize`, and `closed` pull-request actions and Slack `app_mention` events are normalized. GitHub API actions and provider-side GitHub uninstall are missing. Slack posting accepts only a conversation ID and static text; delivery is at least once and can duplicate if a successful post's response is lost. Production custom and provider webhooks can trigger exact `type` matches to versioned HTTP or Slack message workflows. JSON Pointer references in the HTTP JSON body can read from the accepted event; URLs, headers, Slack message text, and response-to-next-step mapping are static. The encrypted HTTP bearer credential is bound to one exact operator-allowlisted hostname.
- Custom webhook signing secrets and workspace bearer credentials are Fernet-encrypted with a required environment-injected key. `python -m scripts.rotate_secrets` re-encrypts stored values and recalculates credential fingerprints in one transaction, but requires a maintenance window; old keys must remain available while old backups exist. Provider-side token revocation is not implemented.
- Production workflow definitions support constrained HTTP and Slack message actions, with manual starts, exact custom-webhook triggers, or durable interval schedules. Schedules run the current published version, use bounded tenant queue admission, and can be paused/resumed/cancelled. They do not support cron or timezone calendars, and schedule management is API-only; a version requiring webhook event data pauses its schedule. Conditional branches, waits, approvals, response mapping, and compensation are missing. Demo Mode has a separate sandbox action allow-list.
- PostgreSQL is the durable queue. It is sufficient for the measured local workload, but independent broker replay/consumer scaling has not been tested. The per-tenant event-ordering lock can become a write bottleneck.
- A repeatable PostgreSQL source-to-target restore drill passes in CI against disposable PostgreSQL 16 databases. Managed backup retention, cloud recovery, and disaster recovery remain unverified.
- The default local stack embeds workers under the API supervisor. A separate worker role is available through `python -m app.worker` and `compose.workers.yaml`; the process boundary is locally tested but has not been exercised in staging. Worker IDs must be unique across deployment hosts.
- Production API/worker startup and the offline key-rotation command require an explicit `sslmode=verify-full` PostgreSQL connection setting. This prevents accidental plaintext/fallback connections, but a real managed database certificate chain and network path have not been verified in staging.
- Real-time progress uses polling-backed SSE over PostgreSQL. Each poll rechecks the session or API token and current workspace membership, so revoked access closes the stream on its next poll. There is no independent real-time gateway or durable notification outbox.
- HTTP and Slack actions share one end-to-end deadline across DNS, connection, and response handling, capped at half the worker lease. Stuck OS resolver calls use a fixed four-slot semaphore and become retryable failures without opening a provider connection. Network outcomes remain at least once: HTTP providers must honor the supplied idempotency key, while Slack posts may duplicate after an ambiguous response or cancellation. Raw webhook bodies and parsed JSON expire on a configurable schedule, but event metadata and dedupe keys remain indefinitely; database backups and WAL may retain pre-expiry copies. Per-endpoint JSON schemas are absent. Apply edge network limits before exposing public ingress broadly.
- Worker failure logs include request, workflow, task, worker, attempt, step, and error-type fields without logging exception contents. The tenant-authenticated Prometheus endpoint exposes queue depth, oldest ready-task age, expired leases, workflow states, side effects, and dead letters. Owners can issue hash-only workspace tokens restricted to `/metrics`; sample scrape and alert rules pass promtool checks and threshold tests. OTLP/HTTP export is verified against a loopback protobuf receiver. No deployed Prometheus, Alertmanager, OpenTelemetry Collector, or trace backend has been exercised. Pool metrics, Grafana dashboards, and provider metrics are absent.
- CI runs Ruff, Mypy, pre-commit, tests with an 80% app coverage floor, Prometheus `promtool` validation, a weekly Python dependency audit, and a Trivy scan of the built runtime image for OS and library vulnerabilities. The runtime image removes pip after installing application dependencies; CI asserts pip is absent. Staging, deployment rollback, and cloud production are not implemented.
- API tokens support viewer/operator/admin role ceilings; fine-grained per-action scopes are not implemented. The typed Python SDK and CLI are implemented locally. A package-index release, complete product UI, final evidence pack, case study, and demo video remain incomplete.
- Current load and query numbers are local synthetic evidence only. See [BENCHMARKS.md](BENCHMARKS.md).
