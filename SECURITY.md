# Security model

## Controls implemented

- Production startup requires complete HTTPS OIDC configuration. Authlib handles discovery, authorization-code exchange, and ID-token verification. RelayCore requires the configured issuer, a non-empty subject, and a verified email claim.
- The browser receives an opaque `HttpOnly`, `Secure`, `SameSite=Lax` session cookie. PostgreSQL stores only its SHA-256 hash; sessions expire and can be revoked. Unsafe cookie-authenticated requests require the configured same-origin `Origin`.
- Production requests resolve a selected workspace through an active membership. Cross-workspace resources return not found. Role checks distinguish owners, admins, developers, and viewers. Membership writes preserve an owner and prevent admins from changing another owner's membership.
- Long-lived SSE streams recheck the active session or API token and workspace membership at every poll; a revoked identity stops receiving later events.
- SQL uses parameterized Psycopg statements; workflow steps are validated against a fixed action allow-list. No workflow payload is evaluated as Python or shell.
- Webhook signing keys are random and Fernet-encrypted in PostgreSQL. Plaintext is returned only at endpoint creation or rotation. HMAC-SHA256 covers the timestamp, event ID, and exact raw body; constant-time comparison, a five-minute freshness window, a 256 KiB body cap, and a unique event key prevent forged or duplicate intake.
- Workspace bearer credentials for GitHub, Slack, and generic HTTP are Fernet-encrypted in PostgreSQL. Owners/admins can create, rotate, list metadata, and revoke them. APIs and audit events never return or log the secret; internal retrieval requires both workspace and credential IDs.
- Production HTTP steps require a credential bound to the exact operator-allowlisted DNS hostname, HTTPS on port 443, and public DNS answers. DNS resolution has a bounded wait and fixed resolver-thread capacity; one end-to-end deadline covers DNS, connection, and response handling and is capped at half the current worker lease. RelayCore pins the validated address while TLS verifies the original hostname; redirects are not followed. Request/response sizes are bounded, credential-like headers/query parameters are rejected, and sensitive JSON response fields are redacted.
- Slack message actions use only the encrypted token for the active Slack installation in the run's workspace. Their bounded payload contains a conversation ID and text; the fixed API URL, pinned Slack address, authorization header, and response details are not exposed to workflow authors. Delivery remains at least once, so ambiguous responses may lead to duplicate posts.
- Production webhook intake stores the signed event and creates matching HTTP/Slack-action runs in one database transaction. The run references the event row; workers resolve explicit JSON Pointer references only in HTTP request bodies. The event payload stays out of run-history API responses and audit metadata.
- GitHub App linking binds a one-use state and PKCE verifier to the signed-in workspace admin. The callback confirms the user can access the installation and separately checks that the installation belongs to the configured App; the user access token is discarded. GitHub deliveries require HMAC-SHA256 over the raw body, use the UUID delivery ID for deduplication, normalize only supported pull-request actions, and pass through the same durable event/run transaction. Internal GitHub endpoints are hidden from custom-webhook management and cannot be rotated or revoked through those routes.
- Slack OAuth state is one-use, short-lived, and bound to the signed-in workspace admin. The callback checks the configured Slack App ID, workspace, bot token type, and requested event scope; the bot token is Fernet-encrypted using the existing workspace credential store. Events API requests require Slack's HMAC-SHA256 signature over the exact raw body and a timestamp within five minutes. Only bounded `app_mention` fields are normalized, Slack event IDs deduplicate retries, and app uninstall or admin disconnect revokes the local token and endpoint. Internal Slack endpoints are hidden from custom-webhook management.
- Structured HTTP logs use request IDs and do not include authorization headers or session values. User-visible dashboard values are escaped before insertion into HTML.
- Request-validation responses include field locations and messages but omit submitted values and validator context, avoiding accidental echo of secrets or webhook payloads.
- Static API keys and simulated provider actions are limited to Demo Mode.
- The worker repeats the Demo/production action-mode check before dispatch. Old queued sandbox actions opened under production settings fail permanently into the DLQ without creating an effect.
- Demo action implementations are isolated in `app/sandbox.py`, which production workers do not import.
- CI builds the production image, verifies the runtime image has no pip package manager, and scans OS and Python library packages with Trivy; a separate `pip-audit` job checks the resolved requirements.

## Unimplemented protections

GitHub API actions, provider-side GitHub uninstall, URL/header templating, and HTTP response mapping are not implemented. GitHub OAuth tokens are not retained or refreshed. The HTTP action allowlist is an operator control and must be kept narrow. Each process has a four-slot DNS semaphore because OS resolver calls cannot be cancelled; when all slots are occupied, new actions fail retryably until a lookup returns. Timed-out lookups do not open provider connections. External delivery remains at least once: HTTP providers should enforce the supplied idempotency key, and Slack does not provide an idempotency guarantee, so ambiguous delivery may repeat a message. `python -m scripts.rotate_secrets` re-encrypts database-held secrets in one transaction, but requires a maintenance window and secure backup/key-escrow handling; it does not rotate provider-side credentials. Raw webhook bodies expire, while event metadata and deduplication records are retained indefinitely. Per-endpoint JSON schemas, edge IP rate limits, invitation flows, MFA/account recovery, and a live third-party security review are pending. Python requirements and the built runtime image are scanned in CI; these checks do not replace live provider verification or a security review.

Production must use a managed PostgreSQL service, TLS at ingress and database connections, a secret manager, network restrictions, backups, and a reviewed OIDC provider configuration. Demo Mode is not a shared production security boundary.
